## 现场问题

把训练改成 FP16 后速度变快，几百步后却出现 `nan`。重启恢复还会在相近位置再次失败。

> 哪些数值在溢出，哪些检查能帮助定位？

<SectionQA id="4.3" mode="ask" />

## 不同格式能表示的范围不同

**混合精度（Mixed Precision）**让不同计算和状态使用不同精度，以平衡速度、内存与稳定性。FP32、FP16 与 BF16 的指数范围和有效精度不同；BF16 的指数范围接近 FP32，但尾数更短。它并不自动让训练免于 NaN。

**Autocast**按操作选择计算类型，并不意味着所有参数和优化器状态都变为低精度。应区分权重存储类型、内核运算类型、累积类型与优化器状态类型。

| 机制 | 解决什么 | 不解决什么 |
| --- | --- | --- |
| autocast | 为适合的操作选择低精度计算 | 数据或目标错误 |
| loss scaling | 降低 FP16 小梯度下溢风险 | 过高学习率和全部数值异常 |
| 梯度裁剪 | 限制梯度整体范数 | 错位标签和无效输入 |
| 有限数检查 | 尽早发现 NaN / Inf | 自动找到根因 |

## 裁剪要发生在正确的梯度上

**梯度范数裁剪（Gradient Norm Clipping）**在范数超过阈值时整体缩放梯度。使用 loss scaling 时，需要先 unscale，再裁剪，再执行优化器步骤。累积尚未完成或梯度尚未正确同步时就裁剪，会改变实际更新。

梯度范数也应进入日志。持续触发裁剪可能提示学习率、数据、初始化或归一化需要检查；不能因为“裁剪后暂时不炸”就认为问题已经解决。

> **一句话听懂**：混合精度决定哪些数怎样表示，裁剪限制更新前的梯度大小，日志负责说明异常何时、在哪批数据上发生。

## 把一次更新的顺序完整写出来

以单优化器、普通 DDP 完整副本、FP16 GradScaler 为例，下表是**机制说明，TinyPretrain 仍只实现 FP32**：

| 时机 | 操作 | 需要保持的约定 |
| --- | --- | --- |
| 开始本次更新 | 清零梯度、确定本次有效 token 分母 | 全局有效数覆盖全部累积材料 |
| 每微批次 | autocast 前向、归一化 loss、`scaler.scale(loss).backward()` | 整次累积使用同一 scale；前 A−1 次 `no_sync()` 覆盖前向和反向 |
| 最后一次反向 | DDP 按约定归约梯度 | 所有 rank 集合通信次序一致 |
| 全部累积结束 | `scaler.unscale_(optimizer)`，仅一次 | 先恢复真实梯度尺度，再检查 / 裁剪 |
| 更新边界 | 完整梯度范数裁剪；`scaler.step(optimizer)` | 若检测到 Inf/NaN，scaler 可能跳过 optimizer.step |
| 更新边界结束 | `scaler.update()`；确认是否真正更新 | 按成功更新计数的 step 与调度器，仅在更新发生时前进 |

单优化器的标准动态缩放中，更新前后 scale 下降可作为溢出跳过的信号；不能用 `scaler.step()` 的返回值是否为 None 判断成功，因为许多优化器成功时也返回 None。多优化器或其他 scaler 实现应使用其明确的更新状态接口。[PyTorch 的梯度累积 / 裁剪说明](https://docs.pytorch.org/docs/2.11/notes/amp_examples.html#gradient-accumulation)要求同一有效批量内 scale 保持一致。

若第 12 次尝试因溢出跳过，已消费的数据和算力仍然发生，但成功更新数不增加。本书默认 FP32 异常即停止，因此 `tokens` 只累计已完成更新的消费量。AMP 工程最好另外记录 consumed-tokens、successful-updates 与 skipped-updates；按 token 调度还是按成功更新调度必须预先定义，并让日志和恢复一致。

<details>
<summary>为什么完整副本裁剪不能直接推广到状态分片？</summary>

普通 DDP 归约后每 rank 有完整梯度，范数可在本地完整参数上计算。FSDP / ZeRO 等方案可能只保留梯度分片，单 rank 的局部范数不等于全模型范数；TP 还要区分分片和重复参数，避免重复计数。应使用所用版本提供的分布式范数 / 裁剪机制，并核对参与组，不把本书 `clip_grad_norm_(model.parameters())` 当作任意布局的通用指令。

</details>

## 用最近证据缩小范围

出现 NaN 时记录最早异常的 loss、梯度和批次，而不是等它传播到权重之后。核对学习率、恢复后的状态、标签范围、掩码是否让某行没有可见位置，以及数据中是否出现异常样本。必要时短暂用 FP32 重跑同一小批次，比较异常是否依旧。

如果多卡中只有一个 rank 先出错，要保存各 rank 的输入身份；集合通信可能把异常传播给其他副本。单机“能跑”不等于分布式状态一定正确。

TinyPretrain 默认采用 FP32，优先让 CPU 实验容易复现。它检查 loss 和梯度范数是否有限，失败时停止写入新的有效检查点；它没有实现完整 BF16/FP16 路径，生产精度切换需要按框架文档单独验证。
