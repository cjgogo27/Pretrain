## 现场问题

训练在第 8,000 步中断。你加载最后的权重继续跑，loss 却出现明显跳变；另一份文件下载完整，加载时才发现写入被打断。

> 一个“能恢复”的检查点应该保存到什么程度？

<SectionQA id="4.6" mode="ask" />

## 保存模型与恢复训练是两种产物

**检查点（Checkpoint）**是某个训练时刻的状态快照。用于推理的权重可以不包含优化器；用于延续同一次训练的快照，则需要更多状态。恢复目标也分层：能加载继续运行、统计上延续、同环境下严格一致，要求逐级提高。

| 状态 | 为什么需要 | 丢失后可能怎样 |
| --- | --- | --- |
| 模型权重 | 学习结果 | 回到更早模型或无法加载 |
| 优化器与调度 | 更新历史与学习率位置 | 下一步更新轨迹改变 |
| step 与 token 计数 | 运行进度 | 调度、日志和预算错位 |
| 各设备随机状态 | 采样、dropout 等 | 后续随机过程改变 |
| 缩放器状态（若使用 AMP） | scale 与增长 / 回退历史 | 溢出处理与后续数值节奏改变；默认 FP32 示例没有这项 |
| 数据游标 / 采样器 | 从哪里继续读 | 重复或跳过数据 |
| 配置、数据、分词器身份 | 解释状态含义 | 在不同任务上误用旧状态 |

## 文件存在不等于保存完成

单机可先写临时文件，完成后在同一文件系统原子替换目标路径。分布式分片检查点则需要确认所有必要分片成功，再提交完成标记与清单。最终还应做完整性与实际加载检查；单机改名不自动提供跨机器事务。

检查点频率需要平衡写入成本与潜在丢失计算。若每次保存耗时较长，过于频繁会明显降低吞吐；间隔太久则增加故障回滚量。依据观察到的故障和保存时间制定策略，并保留多个已验证版本。

> **一句话听懂**：恢复不是“把权重读回来”，而是让参数、更新历史、数据位置与随机过程重新对上同一时刻。

## 真正演练一次恢复

先做固定总计划的连续运行，再做在中间停止、从检查点继续的运行。相同环境下比较最后参数、优化器状态、步数和 token。若硬件、内核或并行度发生变化，严格逐位一致可能不成立，需定义允许的数值误差或统计标准。

教学实验提供恢复验证脚本：固定 CPU、线程、数据与种子，比较连续训练和分段恢复的最终状态。它将配置和数据哈希一并核对；恢复时要求相同 world size，并保存每个 rank 的随机生成器状态。多卡一致性需要在实际目标环境重测。

## “记录过代码”与“约束了代码”不是一回事

旧版本保存 `code_revision` 和 `code_sha256`，却没有在恢复时比较；本轮先复现了“把学习率乘以 1.01 仍被接受”的问题。现在格式版本 2 的严格恢复要求当前 `train.py` 的规范化源码 SHA-256 与快照相同，缺字段或不一致都拒绝。

哈希只规范 UTF-8 BOM 与换行，不忽略代码、注释或空白修改；所有本地训练逻辑目前集中在该文件。它不是数字签名，也不能抵抗人为篡改快照。`code_revision` 保留作来源记录，不强制整个 Git HEAD 相等，因纯文档提交不应让未改变的训练代码失效。PyTorch、数据、计划和 world size 的检查继续保留。

旧格式快照不能被悄悄当成格式 2 严格恢复。若只需要旧权重，应使用 [6.4 的新运行入口](/Pretrain/06-tools-practice/04-continued-pretraining/)，重新建立优化器和计数，并明确它不等于继续原轨迹。

## 从故障中恢复也要留痕

记录中断原因、最后成功检查点、恢复命令和重复消耗的 token。训练 token 可区分“已完成并保留的更新”和“故障后丢弃的实际计算”；只报一个数会混淆优化进度与成本。

只加载可信来源的检查点。完整训练快照可能采用支持复杂对象的序列化方式，本项目的恢复文件也是如此；交付推理权重时应考虑更受限的格式与单独元数据。
