## 先明确假设

以下工具对**稠密语言模型**使用 $C\approx6ND$。它忽略更细的注意力长度项、重计算和实现差异，不能直接用作 MoE、超长上下文或全部生命周期成本的精确预算。

设备速度输入的是每卡在目标负载下的**有效 TFLOP/s**，不是峰值再额外乘利用率。默认 100 仅为演示假设。端到端吞吐测量如果已经包含评估与保存，不应又重复把同一部分计入额外开销。

## 固定算例

| 输入 / 输出 | 数值 | 性质 |
| --- | --- | --- |
| 参数量 | 1B | 假设稠密模型 |
| 消费 token | 20B | 包含重复消费，不代表唯一数据 |
| 设备数 | 8 | 假设 |
| 每卡有效速度 | 100 TFLOP/s | 假设，不对应设备测评 |
| 估计训练 FLOPs | $1.2\times10^{20}$ | $6ND$ |
| 理想计算时间 | 41.7 小时 | 总量 / 有效速度 |
| 每卡微批量 / 长度 / 累积 / DP | 2 / 1024 / 8 / 4 | 另一个独立批量算例 |
| 每更新 token | 65,536 | $bSAP$ |

若预算要求 20B token 且每步 65,536 token，约需 305,176 次更新；最后一步如何对齐预算需在实现中约定。设备数与 DP 不必相等，组合模型并行时更要区分。

## 与短跑校准对应

[3.5 节](/Pretrain/03-model-compute/05-scaling-laws-and-budget/)给出完整的**假设**校准过程：8 卡每更新 131,072 token，100 个更新 / 100 秒得到计算区间吞吐，再把独立的验证和保存时间纳入完整周期。43.7 小时是这个假设周期的估计，不是本项目实测。

## 从估算到排期

在目标硬件跑相同模型、精度、长度与并行方案，记录稳定 token/s 和峰值内存。按端到端范围统计评估、检查点、启动与故障，再说明哪些时间已包含在实测分母。不要将理想计算时间直接写成保证交付日期。
