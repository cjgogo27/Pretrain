## 现场问题

## 从一次参数更新说起

预训练可以沿两条链理解。**数据流（Data Flow）**把原始文档变成批次；**计算流（Compute Flow）**把批次变成梯度和新参数。数据流给计算流提供材料，计算流反复执行。文档通常离线清洗一次，前向与反向则每个微批次都会发生，二者的节奏不同。

下表按职责划分模块。实际工程可以合并进程或拆分服务，这里的“层”用于澄清接口，并不表示每层必须独占一台机器。

| 功能层 | 在一次训练中负责什么 | 向下游交接什么 | 常见检查点 |
| --- | --- | --- | --- |
| 语料与质量层 | 取数、清洗、去重、切分与配比 | 文档分片、来源、数据版本 | 是否混入验证集或重复文档 |
| 分词与批次层 | 编码、拼接、采样与掩码 | token ID、标签、有效位置 | 是否错位、是否学习 padding |
| 模型前向层 | 将历史 token 映射为下一 token 得分 | logits | 张量形状、因果可见性 |
| 损失与反向层 | 计算目标误差、求梯度 | loss、梯度 | 归一化方式、有限数检查 |
| 参数更新层 | 同步、裁剪并更新参数 | 权重与优化器状态 | 全局批量、调度步数 |
| 检查点与评估层 | 保存状态并测量未见数据表现 | 可恢复版本与评估报告 | 完整性、污染、配置一致性 |

<SystemMap />

> **一句话听懂**：预训练系统的核心，是把“哪批数据、哪个位置、哪次更新”准确对应起来；排查问题先沿接口找证据。

## 两种反馈不能混成一件事

每次反向传播计算损失对参数的梯度，优化器据此更新权重。这是**梯度更新环**，一般以微批次和优化器步为节奏。梯度累积意味着多个微批次之后才做一次参数更新。

阶段性评估则读取固定检查点，在冻结的验证集上计算指标。发现某领域变差后，团队可能设计配比或学习率实验。这是**实验反馈环**，通常由人工决策或事先定义的规则驱动。验证集的指标不应该被当成额外训练标签偷偷参与反向传播。

生产系统可能异步评估，但必须把报告绑定到检查点 ID。训练已进行到第 5,000 步，而评估来自第 4,000 步时，不能把二者当成同一时刻的状态。

## 各层共用的基础设施

| 基础设施 | 提供什么 | 出错会怎样 |
| --- | --- | --- |
| GPU、网络与存储 | 算力、通信带宽、样本供给 | 等待数据、通信拥塞、显存不足 |
| 分布式运行时 | 进程组与集合通信 | 某个 rank 卡住，其他进程等待 |
| 日志与追踪 | token 计数、吞吐、梯度与异常 | 无法区分数据问题与数值问题 |
| 配置与版本管理 | 数据、模型、分词器和环境身份 | 相同权重无法复现相同输入 |
| 恢复与交付机制 | 完整写入、校验、重启与格式导出 | 只有文件名，没有可恢复状态 |

PyTorch、Megatron Core 或 DeepSpeed 属于软件与运行时选择，可以支撑多个功能层。不能把“用了某个框架”当成已经完成数据治理、评估或恢复设计。

## 以一次异常为例

如果某一步 loss 突然上升，先记录批次 ID、有效 token 数与数据来源；再看梯度范数、学习率、是否刚恢复训练；最后结合每个 rank 的日志检查输入和同步情况。只有平均 loss 而没有这些上下文，通常无法还原问题。
