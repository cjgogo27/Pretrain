## 现场问题

把一份文本放进目录，启动程序，屏幕开始显示 loss，随后出现检查点。可是检查点恢复后，loss 突然跳变了。

> 同一段文字经过了哪些接口？要找到跳变原因，应该留下哪些证据？

本节沿一个短文档走完一次更新。字节 ID 是真实编码结果，概率是手算设例；训练实测在 [6.2 节](/Pretrain/06-tools-practice/02-minimal-pretraining/)单独报告。

## 先给这段文本一个明确身份

选用短文档 `Hi!`，避免把汉字误当成一个字节。本书教学编码为 **UTF-8 单字节 ID**：普通字节 0–255，另设文档结束 EOS=256。下面不是某个商业分词器的示意 ID，可以直接核对：

```python
list("Hi!".encode("utf-8"))  # [72, 105, 33]
# 文档编码后追加 EOS，得到 [72, 105, 33, 256]
```

实际数据先清洗、按文档划分，再分别编码 train / val。原始文件哈希、编码规则和划分共同标识输入；不把验证文档拼进训练流。生产数据还可能打包到分片，第 2 章会进一步说明。

## 同一个例子怎样变成一次更新

为便于手算，令微批量 B=1、长度 S=3、累积 A=2、数据并行 DP=1。**这不是程序默认的 B=4、S=64、A=1。**第一个微批次恰好读取四项 token 流：

```text
input_ids = [[72, 105, 33]]   # H, i, !
labels    = [[105, 33, 256]]  # i, !, EOS
loss_mask = [[1, 1, 1]]      # 3 个有效预测位置
```

标签已在外部右移，模型内不再移动。位置 0 只看 H，预测 i；位置 1 看 Hi，预测 !；位置 2 看 Hi!，预测 EOS。整段可以并行计算，因果可见范围仍要逐位置限制。这里 `loss_mask` 是概念上的全 1；实际教学代码无 padding，直接对所有位置计损失，不单独分配这个张量。

| 预测位置 | 允许看到的输入位置 | 正确标签 | 假设给标签的概率 | token loss（自然对数） |
| --- | --- | --- | --- | --- |
| 0 | 0 | 105 | 0.5 | 0.6931 |
| 1 | 0、1 | 33 | 0.25 | 1.3863 |
| 2 | 0、1、2 | 256 | 0.125 | 2.0794 |

前向先查嵌入、经过因果 Transformer，再输出 `logits [1,3,257]`。表中概率是对每个位置的 257 项得分做 softmax 后取标签对应项的**假设值，不是实测**。交叉熵接收原始 logits，平均损失为 `(0.6931+1.3863+2.0794)/3 ≈ 1.3863`。

反向传播计算这个平均损失对参数的导数。为便于一直追踪同一对象，本例第二个微批次再次使用同一个 `Hi!` 窗口；生产训练通常采不同窗口。第一次用 `loss/2` 做 backward，第二次也如此，最后 `.grad` 表示两份等有效 token 数材料的共同更新方向。若有效数不同，就不能机械除以 2，见 [4.1 的 100/900 算例](/Pretrain/04-training-distributed/01-loss-and-gradients/)。

完成累积后检查、裁剪梯度，AdamW 结合一二阶矩更新权重；更新成功后 optimizer-step 加 1，累计训练 token 加 `1×3×2×1=6`。这 6 个是消费的预测位置，可能来自重复窗口，不等于 6 个唯一新 token。多个 DDP 副本中，最后一次反向通常已完成梯度归约；损失缩放必须配合归约的均值语义。[1]

## 把职责、交接物和执行时机对上

| 模块 | 接收 → 操作 → 输出 | 执行时机 | 出错时检查的依据 |
| --- | --- | --- | --- |
| 数据准备 | 文档 → 清洗、划分、编码 → token 流与清单 | 数据版本改变时离线重建 | 原文、划分、文件哈希、编码 ID |
| 批次构造 | 流与窗口索引 → 取 S+1、右移 → 输入、标签、有效位置 | 每个微批次 | 同一窗口 ID、目标、可见矩阵、有效数 |
| 前向 | 输入、位置与 attention mask → 因果网络 → logits | 每个微批次 | `[B,S,V]`、词表范围、未来扰动测试 |
| 损失与反向 | logits、标签、loss mask → 归一化并求导 → loss 与梯度 | 每个微批次；梯度先累加 | 损失总和 / 有效数、有限数、梯度范数 |
| 同步与更新 | 梯度、优化器、lr → 归约、裁剪、AdamW → 新权重与状态 | 每 A 个微批次一次；DDP 同步可与反向重叠 | DP 组、归约均值、实际 lr、是否真正更新 |
| 验证 | 固定验证窗口与指定权重 → 无梯度前向 → 指标报告 | 指定更新边界，或生产中的异步任务 | 数据 / 窗口身份、分母、权重步数 |
| 保存 | 权重、优化器、计划、身份、RNG → 临时写入并提交 → 检查点 | 指定更新边界 | 完整文件、格式、代码哈希、实际恢复对照 |

<SystemMap />

> **一句话听懂**：一次预训练更新，是让同一批数据、同一组预测位置、同一份梯度和同一时刻的状态准确对应起来。

## 两种反馈，改变的是不同对象

**梯度更新**改变权重与优化器状态，遵循已定计划。**实验反馈**在验证发现退化后，提出新的数据配比或学习率候选，再用受控实验比较。验证指标不会自动变成当前训练批次的标签。

同步验证若发生在第 20 次更新后，报告绑定该权重版本；异步评估若读取第 4,000 步检查点，即使训练已经到第 5,000 步，也必须标明结果来自 4,000。检查点是状态快照，验证是测量，二者可以同时发生，但职责不同。

## 用“恢复后 loss 跳变”沿证据排查

先区分“随机 train loss 不同”和“同一固定窗口预测改变”。随机窗口本来有不同难度；固定输入对照能减少这个混淆。

| 观察证据 | 候选解释 | 最小确认方法 |
| --- | --- | --- |
| 数据 / 编码哈希变化 | 输入分布或 ID 含义变了 | 对照清单和窗口 ID；严格恢复应拒绝 |
| 同一恢复步的 lr / 总计划不同 | 调度终点、累积或全局批量变了 | 对照配置与下一步 lr，核算 token/更新 |
| 首个固定前向相同，更新后分叉 | 优化器矩、裁剪、lr 或更新代码变化 | 比较更新前梯度与 optimizer state，再执行一小步 |
| 下一批窗口次序不同 | 训练采样器 / RNG 未恢复 | 比较保存状态和下一组窗口索引 |
| 仅多进程出现偏差 / 卡死 | rank 数据、损失缩放或通信次序错误 | 保存逐 rank 计数，用 [6.3 固定样本对照](/Pretrain/06-tools-practice/03-single-to-multi-gpu/)核对 |

代码本身也可能改变学习率。因此严格恢复要核对训练代码哈希，而不仅仅保存它。配套测试会保存检查点，再把学习率乘以 1.01，确认修改代码被拒绝；这检验身份约束，不等于证明所有实现都正确。

## 所有模块共用哪些支撑

CPU/GPU 执行计算，存储提供 token 流与快照，通信连接 rank，日志保存样本、token、loss 与梯度，配置和版本管理让它们属于同一运行。PyTorch、DeepSpeed、Megatron 可以参与多个环节，硬件也可由多个功能共享。[2]
