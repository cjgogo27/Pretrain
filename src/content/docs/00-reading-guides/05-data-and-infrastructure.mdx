## 同一份模型代码，为什么项目结果仍会不同

假设团队计划用32张GPU训练。一组改进清洗后，代码缩进丢了；一组把卡申请齐了，数据却没及时到；第三组训练遇到节点退出，重启后重复了一段输入。三组都能执行相同的交叉熵，问题却分别在**学习材料、交付材料的系统、保存学习进度的系统**。

预训练的核心需要同时看数据、学习方法和**训练基础设施（Infrastructure，Infra）**。算法说明如何更新，数据决定反复学习什么，Infra保证这些更新在资源和故障约束下正确执行。这是职责划分，不给“数据占多少%、系统占多少%”的固定工作量配方。

## 数据是一条完整的工程链

| 阶段 | 接收 → 交出 | 开跑前留下什么证据 |
| --- | --- | --- |
| 获取与解析 | 来源快照 → 带来源ID的文档 | 来源、可用范围、解析版本和失败清单 |
| 清洗与去重 | 文档 → 保留/拒绝决定 | 规则版本、分层抽查、误删/漏删反例 |
| 划分与去污染 | 来源组 → train/dev/test | 原题/改写分组、重复检查范围和污染盲区 |
| 分词与打包 | 文档 → token分片与边界 | tokenizer身份、EOS、position/attention/loss约定 |
| 配比与供给 | 分片 → 有序逻辑窗口 | 请求比例、实际有效token、重复消费与数据游标 |
| 实验反馈 | 固定评测 → 下一版数据候选 | 固定模型/预算的对照，而非同时改三项 |

2.1的三种子配比结果、2.2的误删/漏删已经实跑，仍保留原始边界：清洗夹具没有拿去训练，不能把配比收益写成清洗收益。**清洗通过、loader快、模型任务好**是三种证据，不能互相替代。

## Infra具体负责哪些工作

| 系统职责 | 交接对象 | 可观察的故障信号 |
| --- | --- | --- |
| 资源与拓扑 | 节点/设备/互联、作业配额 | 资源凑不齐、跨慢链路高频通信 |
| 数据供给与存储 | 分片、缓存、预取队列 | 数据等待、冷热缓存差异、损坏分片 |
| 并行执行 | TP/PP/CP/DP/EP进程组 | 组成员错、通信次序错、最慢rank拖尾 |
| 内存与数值 | 参数/激活/优化器、精度 | OOM、重计算增加、非有限梯度 |
| 调度与容错 | 启动、抢占、快照、重建worker | 重启循环、快照不完整、游标重复/跳过 |
| 可观测与交付 | 配置、版本、计数、trace、报告 | 只看GPU busy，解释不了已交付进度 |

并行策略决定一次模型计算怎样合作；**作业调度**决定什么时候给哪些资源；学习率调度决定更新时lr怎样变化。三种“调度”不能混用。系统也不只是GPU：CPU解析、主存预取、网络、共享存储、控制面都可能限制端到端进度。

## 把三个问题放到一次验收里

1. **材料是否合适？** 对同一数据版本检查内容、来源组、token分布与小模型探针。
2. **学习是否按计划？** 核对有效token、全局batch、梯度归约、学习率与固定评测。
3. **结果是否保留下来？** 核对完成的更新、检查点提交、故障丢弃计算和恢复后的下一批ID。

例如数据配比改成更多长代码，除了领域loss，还要复查长度、打包效率、数据供给和负载。不能因为是“数据改动”就跳过系统测量，也不能为提高吞吐悄悄改变采样分布。
