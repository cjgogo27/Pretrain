## 先把系统接口对上

你可能负责数据、训练、平台或评测中的一段。建议先读 [1.3 系统架构](/Pretrain/01-system-overview/03-pretraining-system-architecture/)，把自己负责的输入、输出和上下游画出来，再按需要补齐相邻模块。

| 你的工作 | 优先顺序 | 读完应该能回答 |
| --- | --- | --- |
| 数据工程 | 2.1 → 2.2 → 2.3 → 2.4 → 2.5 | 这批 token 来自哪里，边界与版本是什么 |
| 模型训练 | 3.2 → 3.4 → 4.1 → 4.2 → 4.3 | 哪个计数推进学习率，梯度怎样归一化 |
| 平台与集群 | 3.4 → 4.4 → 4.5 → 4.6 → 5.4 | 状态、激活和通信哪个是瓶颈 |
| 评测与交付 | 5.1 → 5.2 → 5.3 → 6.5 | 报告绑定哪个检查点，比较条件是否一致 |

## 用一项实验落地

运行 [6.2 最小实验](/Pretrain/06-tools-practice/02-minimal-pretraining/)，打开 `metrics.jsonl`，对照输入、更新和保存过程。重点做一次暂停恢复与一次数据变更后的拒绝恢复验证。

再运行 `python examples/verify_ddp.py`，核对 100 / 900 个有效 token 下的单进程与两 rank 梯度、更新和固定窗口 loss。它是数值对照，不是扩展性能测试。阶段切换时按[训练阶段怎样连接](/Pretrain/00-reading-guides/04-training-stages/)记录数据、lr、长度、检查点和评估身份；只加载权重的新阶段使用 6.4 的入口。

每节的“工程师”问题检查接口与实现；学生问题补概念，产品/PR 问题帮助跨部门沟通。回答不出时回到系统图，沿交接的数据查，而不是先猜框架参数。

接着运行 `python examples/verify_ddp_training.py`，核对多步累积 / 裁剪，以及真实训练循环的两 rank 保存与恢复。数据侧看 2.1 / 2.2 的实跑，性能侧看 4.5 的字节与气泡分母、5.4 的等待剖析；先保留证据，再选改动。

## 推荐实践清单

1. 写出批次、长度、累积与数据并行副本，计算每次更新 token。
2. 给数据和分词器建立可核对的身份。
3. 记录目标硬件上的峰值、吞吐与恢复测试结果。
4. 把模型交付与训练恢复所需文件分别列清。

这条路线可以按工作模块阅读，不要求一次通读。公式的前提和算例单位仍然要核对，尤其是将稠密模型估算迁移到长上下文或 MoE 时。
