## 现场问题

单卡训练正常，切到两张 GPU 后速度提升不大，最终损失也变了。你发现全局批量翻倍了，每个 rank 还在读取相同的数据。

> 扩卡时，哪些变化是预期的，哪些是实现错误？

<SectionQA id="6.3" mode="ask" />

## 一个进程对应一张 GPU

**torchrun**启动多个工作进程，并提供 rank、local rank 和 world size 等环境信息。训练脚本据此设置设备、初始化进程组，并用 DDP 包装模型。每个进程应绑定自己的设备，不能都默认使用第 0 张卡。

Linux 的两张 CUDA GPU 示例：

```bash
torchrun --standalone --nproc_per_node=2 examples/train.py --device cuda --data runs/data --out runs/ddp --steps 100 --batch-size 2 --accum 2 --eval-windows 16
```

此命令使用 NCCL，前提是环境、驱动、PyTorch 构建和设备可用。Windows 原生不提供 NCCL，GPU 多卡请使用支持的 Linux / WSL 环境；本项目不声称已验证 CUDA 多卡。CPU 通信机制可用 `--device cpu` 和 Gloo 做本机小测试。

## 批量要重新算

两卡、每卡批量 2、累积 2、长度 64，一次更新消费 $2\times2\times2\times64=512$ 个 token。要与单卡相同全局批量比较，需要调整每卡批量或累积，而不是只改进程数。

| 要核对的接口 | 正确行为 | 异常线索 |
| --- | --- | --- |
| 设备绑定 | 每进程使用对应设备 | 多进程挤在第 0 卡 |
| 数据流 | rank 独立且可记录 | 完全相同批次反复出现 |
| 通信次序 | 所有 rank 一致 | 某进程先退出，其他卡死 |
| 保存 | 所需状态汇集，统一提交 | 多 rank 覆盖同一个文件 |
| 评估 | 按有效 token 汇总 | 直接平均不同分母的 loss |

> **一句话听懂**：多卡首先是多个进程对数据、梯度和进度达成一致，其次才是增加计算速度。

## 先做小的等价检查

在可控数据和配置上验证参数初始一致、每步都完成同步、各副本权重相同、token 计数正确、暂停恢复可加载。分布式归约顺序可能产生浮点差异，不应要求与不同并行布局逐位相同。

教学脚本在每次保存时收集每个 rank 的随机状态。恢复要求相同 world size；改卡数继续训练属于重新规划数据与批量的迁移场景，不在严格恢复范围内。

## 固定样本数值对照：本轮已运行的 CPU 两进程测试

```bash
python examples/verify_ddp.py
```

不需要下载数据。脚本固定模型初始化和 100 个长度 10 的输入窗口：rank 0 分到 10 个窗口（100 有效 token），rank 1 分到 90 个（900 token）。单进程在全部 1,000 token 上求平均；DDP 每 rank 用 `2×local_loss_sum/1000` 反向，与 [4.1](/Pretrain/04-training-distributed/01-loss-and-gradients/)相同的归约假设对应。之后各自执行一次相同 AdamW 更新，未加入裁剪或 AMP，以隔离归约问题。

| 实测比较（Windows / PyTorch 2.11 CPU） | 最大绝对差 |
| --- | --- |
| 全参数梯度 | 1.490e-08 |
| 一次 AdamW 后的参数 | 1.050e-07 |
| 固定验证窗口的平均 loss | 1.907e-07 |

成功条件为梯度与更新 `atol=1e-6, rtol=1e-4`，验证 loss 绝对差不超过 `1e-6`，且两 rank 的窗口身份与单进程相同。脚本对**全部参数**逐项检查，不只比较一个总 loss。

验证索引由一个全局种子生成，共 8 个窗口；单进程读取全部，两进程分别读取 `indices[0::2]` 与 `indices[1::2]`，最后按 NLL 总和 / 有效 token 总数汇总。每个索引只分配一次，不代表窗口内容没有重叠。

本机 `torchrun` 默认 TCPStore 受 libuv 支持限制；该对照脚本显式创建 `TCPStore(use_libuv=False)` 并启动两个 Gloo 进程。运行中出现地址连接重试警告，最终完成并通过。成功会打印 `status: PASS` 和误差；若构建无 Gloo、端口不可用或超时，应保留错误，不能把它记为通过。

产物是终端 JSON 和测试自己的临时文件（结束时清理）。这个脚本只验证单步数值路径；多步与真实训练循环由下面另一项实验覆盖，不能混作同一测试。

## 从一次更新走到多步与重启

```bash
python examples/verify_ddp_training.py --out runs/ddp-training
```

程序生成 `report.json` 和 continuous / paused / resumed 三份日志，包含两层检查。都已在 Windows / Python 3.12.5 / PyTorch 2.11.0+cpu 上实际运行，FP32、每进程 1 线程、两进程 Gloo；使用 `TCPStore(use_libuv=False)`。

**第一层：同样本，比较五次更新。** 模型 width=16、1 层、S=8；每更新固定 8 个全局窗口，共 64 个目标位置。单进程一次读取全部；DDP 按窗口索引 `rank::2` 划分，每 rank B=2、A=2。第一个微批次的前向与反向都在 `no_sync` 内，每个局部平均 loss 除以 2，第二个微批次归约后才裁剪、AdamW 更新。完整梯度副本的裁剪阈值 0.2，每步实测均触发裁剪。

| 五步内、两 rank、全部参数的比较 | 实测最大绝对差 |
| --- | --- |
| 裁剪前梯度 | 3.7253e-08 |
| 裁剪前范数 | 5.9605e-08 |
| 每步更新后参数 | 2.5115e-07 |

逐参数使用 `atol=1e-6, rtol=1e-4` 验收，五步均通过。它检查相同输入 / 初始化 / 更新配置的数值等价；不同布局的归约顺序不同，不要求逐位一致。完整 DDP 副本的本地范数裁剪不能直接照搬到分片参数。

**第二层：直接运行 `train.run`，比较同布局恢复。** 模型 width=32、1 层、S=16、每 rank B=2、A=2、DP=2，每更新 `2×16×2×2=128 token`。使用领域概率 0.5，计划均为 8 步：一条连续运行，另一条在第 4 次更新边界正常保存退出，用新进程恢复到第 8 步。

最终 **step=8、tokens=1,024**；模型、AdamW、两 rank 各自的 Python / torch / 采样随机状态、领域消费量与计数逐元素一致。最终 lr、train / val loss、范数、验证索引身份和生成文件也一致。全局领域 / 通用消费为 480 / 544 token。更改配比或领域池文件后严格恢复均拒绝。完整结果见 [ddp-training-reference.json](https://github.com/cjgogo27/Pretrain/blob/main/examples/results/ddp-training-reference.json)。

想自己观察日志，可使用同一个轻量启动入口：

```bash
python examples/prepare_data.py --out runs/ddp-data --pools
python examples/launch_cpu.py --data runs/ddp-data --out runs/ddp-demo --steps 8 --warmup 2 --width 32 --layers 1 --seq-len 16 --batch-size 2 --accum 2 --eval-every 4 --eval-windows 8 --domain-weight 0.5 --clip 0.2
```

`launch_cpu.py` 只负责两进程本机 rendezvous，随后调用原训练函数，不另写训练逻辑。端口 / Gloo 不可用会失败，不能当作通过；目录冲突时另选 `--out`。本机有地址连接重试警告，最终完成。原生诊断与 Python 编码可能混用，验证捕获使用 UTF-8 并替换无法解码字节，仍核对 ASCII 错误身份。

成功条件是两层断言全通过，不是只见 loss 下降。第二层验证的是**同布局、更新边界的正常保存和进程重启**，不是写盘中途断电或 rank 崩溃。没有验证 AMP、分片、CUDA/NCCL、多机、弹性改卡数或扩展性能；8 步也不是长时间稳定性验收。

## 然后再测扩展效率

固定比较目标和全局批量，测稳定步骤的端到端 token/s，观察通信、数据等待与最慢 rank。极小模型常受通信与进程调度主导，两卡比单卡慢并不奇怪。生产规模还要验收分布式存储、网络和分片检查点。
