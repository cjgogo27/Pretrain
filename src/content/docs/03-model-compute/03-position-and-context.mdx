## 现场问题

你把上下文配置从 2,048 改为 32,768，程序能够启动，却在长文本后半段表现很差。另一次尝试中，它甚至直接超出位置表范围。

> 上下文长度只是一个配置开关吗？

<SectionQA id="3.3" mode="ask" />

## 模型需要知道顺序

注意力按内容比较位置，如果没有额外顺序信息，无法仅靠这一操作理解 token 的先后。**位置编码（Positional Encoding）**让位置信息进入网络。可学习绝对位置嵌入把位置映射到向量并与 token 表示相加；**旋转位置编码（RoPE）**则对 Query/Key 的部分维度施加与位置相关的旋转。

不同方案具有不同外推行为。可学习表超过已分配位置会越界；RoPE 数学上能计算更大位置，但模型是否在更长距离上可靠工作，还取决于训练分布和扩展方法。

| 改变什么 | 立刻影响什么 | 还需要验证什么 |
| --- | --- | --- |
| 最大位置表 | 可索引的位置范围 | 新位置是否训练过 |
| RoPE 缩放方式 | 位置间的相位关系 | 长度分层的性能退化 |
| 训练序列长度 | 激活、注意力与批量 | 长文本样本质量与优化稳定性 |
| 推理上下文上限 | 缓存与服务内存 | 检索、引用、跨段依赖能力 |

## 长度带来哪几种成本

标准稠密注意力的分数矩阵随 $S^2$ 增长，投影与前馈通常随 $S$ 增长。FlashAttention 类方法减少对大中间矩阵的显式存储和读写，但不会把标准全注意力的主要计算量变成与长度无关。

因此，把上下文翻倍不必让端到端训练成本精确翻四倍：总成本由注意力、前馈、批次、内核和通信共同决定。要在目标长度上实际测量，而不是只套一句“二次方”。

> **一句话听懂**：支持输入更长、在长文本上训练过、真正能利用远处信息，是三个需要分别验证的条件。

## 怎样评估长上下文

按长度区间报告验证损失，再加入明确需要远程信息的任务。检查答案所在位置、干扰内容、提示格式和截断方式。只测“把一句话藏在长文本里能否找出”，不足以覆盖跨段推理、结构理解和稳健引用。

教学模型采用长度 64 的可学习位置表。生成时仅保留最近 64 个字节 token；这会丢弃更早上下文，而不是自动扩展位置能力。配置与代码中明确使用相同上限，帮助读者看到这个接口约束。

若要扩展已有基础模型，应把位置方案、长序列数据、训练计划与评估一起变更，并保留短上下文回归测试。
