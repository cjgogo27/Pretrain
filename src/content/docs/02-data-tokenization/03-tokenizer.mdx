## 现场问题

你训练出一套新分词器，想直接给已有模型换上。词表大小甚至没有变化，模型却输出了奇怪的文本。

> ID 的数量没变，为什么模型像是突然看不懂字了？

<SectionQA id="2.3" mode="ask" />

## 编码的约定就是模型接口

**分词器（Tokenizer）**将文本编码为 token ID，并按同一约定解码。模型的嵌入表第 100 行与输出第 100 个得分，都对应词表中 ID 100 的含义。如果换了 ID 到文本片段的映射，相当于把模型熟悉的字典打乱。

分词器不仅包含词表，还可能包含规范化、预切分、合并规则、特殊 token 和后处理。发布模型时需要一起保存这些文件与版本。对话模板是另一层输入格式，也应记录，但不等同于分词算法本身。

## 三种常见思路

| 思路 | 基本做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| 字符级 | 以字符为基本单位 | 容易理解，文字边界直观 | 字符集和序列长度问题 |
| 字节级 | 将文本编码成字节单位 | 基础覆盖可做到完整 | 非 ASCII 文本可能需要更长序列 |
| 子词级 | 学习常见片段，如 BPE、Unigram | 在词表规模与长度间折中 | 训练数据和规则影响语言覆盖 |

字节级 BPE 仍然会将常见字节序列合并，不能与“每个字节永远对应一个 token”的教学编码混淆。SentencePiece 是工具与处理框架，支持不同模型；BPE 是其中一种算法思路。

## 词表大小怎样影响系统

词表越大，常见片段可能用更少 token 表示，但嵌入与输出层通常更大。隐藏维度为 $d$、词表为 $V$ 时，单个嵌入矩阵包含 $Vd$ 个参数。输入输出共享权重可以减少参数存储，并不会让输出 softmax 的计算免费。

对某语言来说，分词更碎意味着同样字符数占更多上下文、消耗更多训练 token。应在代表性语料上测字符/token、字节/token、未知或回退情况，而不是只比较词表大小。

> **一句话听懂**：分词器规定模型读写数字的共同语言；权重和分词器必须配套交付。

## 在教学实验中看见它

TinyPretrain 使用 `text.encode('utf-8')`，ID 0–255 对应字节，256 对应 EOS。它不需要训练分词器，便于离线复现。生成时可能截断在一个 UTF-8 字符中间，演示解码使用替换模式处理无效片段；这正说明字节输出不自动保证自然语言质量。

若以后改为 BPE，必须重新构建 token 数据、更新词表维度并重新训练或明确实施嵌入迁移；单改配置文件并不足够。下一节讨论 token 流怎样成为训练批次。
