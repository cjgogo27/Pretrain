## 现场问题

GPU 显示已经分配了大量显存，但每秒 token 很低。你尝试增大 batch，速度没有明显改善，反而遇到 OOM。

> 显存占满、GPU 利用率高和训练高效，是同一件事吗？

<SectionQA id="5.4" mode="ask" />

## 先定义吞吐分子和分母

**训练吞吐（Throughput）**通常用有效训练 token/s 表示。需要说明是单卡还是全局、是否计入 padding、是否包含数据加载、评估和保存。两个数字如果一个只计内核时间、另一个计端到端时间，就不能直接比较。

CUDA 计算通常异步执行。测量短区间时需要正确同步或使用设备事件，避免把“提交完成”当成“计算完成”。正式性能测量先预热，再记录多个稳定步骤，报告波动和配置。

| 观察 | 可能原因 | 下一份证据 |
| --- | --- | --- |
| GPU 间歇空闲 | 数据加载 / CPU 准备跟不上 | batch 等待时间与 CPU 时间线 |
| 通信占比高 | 小算量、拓扑或同步过多 | 通信追踪与缩放曲线 |
| 单个 rank 很慢 | 数据、设备或网络不均 | 每 rank 的 step 时间 |
| 显存高但吞吐低 | 激活大、碎片或低效算子 | 峰值分配与算子 profile |

## MFU 要把口径写出来

**模型 FLOPs 利用率（Model FLOPs Utilization，MFU）**常用“估计的模型训练 FLOPs/s ÷ 对应精度硬件峰值”计算。若用 $6N$ 近似每 token 的训练量，估计 MFU 可写成 $6N\times\text{token/s}/(P\times F_{peak})$。

长上下文的注意力项、重计算、稀疏峰值与精度选择都会影响解释。若把不对应的稀疏硬件峰值用于稠密训练，分母就失真。模型 FLOPs 与硬件实际执行 FLOPs 也不是同一个量。

> **一句话听懂**：显存告诉你存了多少，吞吐告诉你完成了多少，profile 告诉你时间花在哪里。

## 重计算增加了工作，MFU 分子要不要跟着加？

采用 PaLM 的模型口径时，MFU 分子是完成这些训练 token 所需的**约定模型计算量**，不因实现为节省激活而重跑前向就自动增加。硬件实际执行的浮点运算还包含重计算等额外工作；以这类执行量估计的是另一种硬件利用口径。两者不能都叫同一份 MFU。[PaLM §4.1 与 Appendix B](https://arxiv.org/html/2204.02311v5#A2)明确区分这两种计算量。

假设模型口径每步 100 TFLOPs，硬件为重计算实际做了 130 TFLOPs，用时 1 秒，设备峰值 200 TFLOP/s：模型口径 MFU=50%，硬件执行口径利用率=65%。这组数字仅是算例，130 不是实测；真实执行量需要 profiler 或可靠的算子统计支持，不能仅靠 GPU busy 百分比换算。

因此报告需注明 6N 近似是否补入长注意力项、重计算是否排除、吞吐时间是否包含通信和 I/O，以及峰值的精度与稀疏假设。增加重计算后，即便 GPU 更忙，完成同样模型 token 的速度仍可能降低。

## 一次只改变一个瓶颈

先固定模型、长度、全局批量和精度，收集数据等待、前向、反向、通信和更新的时间。判断瓶颈后再调整预取、微批量、累积、内核或并行布局。调整后复测质量和数值，避免为了速度改变了训练含义。

如果保持全局批量不变增加卡数，可观察强扩展效率；保持每卡工作量不变则更接近弱扩展，整体批量也随之改变。结果要注明是哪一种实验。

教学脚本的 token/s 包含循环中评估、日志与保存的时间，用于端到端观察，不用来宣称内核性能。CPU 短跑受启动和线程影响很大，也不外推 GPU 训练速度。
